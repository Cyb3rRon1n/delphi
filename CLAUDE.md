# CLAUDE.md

Guidance for working in this repo.

## What this is

A Chrome MV3 extension: hand it a practice question (select text, drag-capture a region, screenshot the whole page via "check this page," or let opt-in auto-detect find one), get an LLM explanation with the answer hidden behind a reveal. Self-study tool, deliberately **not** built for live/proctored exams — see README's "Not for live/proctored exams" section before adding any feature that leans toward continuous/covert monitoring. That line is a scope boundary, not a suggestion. **The one invariant that must never break: every LLM call traces back to an explicit user click.** Auto-detect finds candidates and offers a button — it must never itself call `generate()`. "Explain all" is still consistent with this: one click, on a feature the user deliberately invoked, that the user knows will fan out to multiple calls — not detection silently triggering anything.

## Architecture

No build step — MV3 supports ES modules natively, so `src/background.js` and everything it imports (`src/lib/`, `src/providers/`) use plain `import`/`export`. `src/content.js` is a classic script (injected via the extension API's `scripting.executeScript({files: [...]})`, not an ES module) since dynamically-injected files can't be declared as modules — it reaches `src/lib/detect-questions.js` via a runtime `import(api.runtime.getURL(...))` instead, which is why that path is listed in `manifest.json`'s `web_accessible_resources`.

**Cross-browser: every file that touches the extension API opens with `const api = globalThis.browser ?? chrome;` and calls `api.*`, never `chrome.*` directly.** This isn't just a naming preference — Firefox exposes `chrome.*` too, but only in callback form (no promises), while every call site in this codebase is `await`ed or `.then()`ed. Using bare `chrome.*` would silently break (not throw — just return `undefined` instead of a promise) on Firefox. `browser.*` is promise-based on Firefox and simply doesn't exist on Chrome/Brave, so the fallback is safe and needs no feature-detection beyond the `??`. Each file declares its own `api` const (background.js, content.js, sidepanel.js, options.js, providers/index.js) rather than sharing one import — content.js in particular can't `import` anything at top level (classic script), and four one-line consts was less machinery than a shared module for this. **`manifest.json`'s `background` key is `service_worker` only — a second, still-open gap, not a solved one.** It briefly also carried `scripts` (Firefox's MV2-era background-script key, since Firefox never ran true MV3 service workers) on the assumption both engines would just ignore the key they don't use, matching the `sidebar_action` assumption above — wrong the same way: Chrome doesn't silently ignore `background.scripts` in an MV3 manifest, it warns/rejects it ("background scripts require manifest version 2 or lower"). Reverted for the same reason `sidebar_action` was. **Whether `background.service_worker` alone actually starts Firefox's background context at all is unconfirmed** — this needs checking against current Firefox docs/an actual Firefox load before claiming Firefox background scripts work, not assumed. `browser_specific_settings.gecko` still pins `strict_min_version: "121.0"` (Firefox had a real bug before 121 where background wouldn't start at all with `service_worker` present) — that constraint is real regardless of how this gap resolves. **The `chrome-ai` provider needs zero cross-browser handling** — it already checks `typeof LanguageModel === "undefined"` and fails soft, which is exactly "unavailable" on both Firefox (no Prompt API) and Brave (doesn't ship Chrome's on-device component); Ollama/Custom already work identically everywhere since they're just `fetch()`.

**None of this — cross-browser or the side panel — has been run against a real Firefox or Brave instance yet** — same "couldn't launch a browser here" constraint as the original Chrome build. Verify before trusting it, the same way Chrome's build was verified in an earlier session (see the Testing section).

**Nothing runs until the user acts.** There's no `content_scripts` entry in `manifest.json` — `src/content.js` is injected on demand by `background.js`, only after a context-menu click, a keyboard command, or the side panel's auto-detect toggle. **`host_permissions: ["<all_urls>"]` is now declared** (see below for why activeTab-only didn't survive contact with the side panel) — injection is still always user-triggered, this permission is about *which tabs* it's allowed to reach, not *when*.

**Side panel replaced the old popup entirely** (`src/popup/` is gone) — `background.js` calls `api.sidePanel.setPanelBehavior({openPanelOnActionClick: true})` so the toolbar icon opens `src/sidepanel/sidepanel.html` docked, instead of a popup that closes on any outside click. `sidepanel.js` is a real module page (unlike `content.js`), so it statically `import`s `buildResultBody` from `src/lib/render-result.js` — pulled out of `content.js` into its own module specifically so both places render results identically instead of drifting into two copies; `content.js` now reaches it via dynamic `import()` same as `detect-questions.js`, since it's still a classic injected script and can't use a static import.

**Why `host_permissions: ["<all_urls>"]` exists — activeTab-only was tried first and confirmed not to work, not skipped as an assumption.** Chrome grants `activeTab` at the moment the side panel is opened (or the toolbar icon clicked, etc.) — for *that* tab, at *that* moment. The panel then stays docked across tab switches, and switching tabs is **not** itself a qualifying gesture, so toggling auto-detect for a tab switched to after opening the panel had no valid grant (`scripting.executeScript` threw "extension manifest must request permission to access the respective host" — a real bug hit and confirmed live). First fix attempt: asked the user broad-permissions-vs-constrained, they chose constrained, so `setAuto()` was made to fail soft instead (try the injection, return `{ok:false, error}` on failure, `sidepanel.js` reverts the checkbox and shows the message) with the workaround "click the toolbar icon once on the tab you want, then toggle." **That workaround was then tested live and doesn't actually work**: with `openPanelOnActionClick: true` and the panel already open, re-clicking the toolbar icon is very likely a no-op (there's nothing to "open"), so it generates no fresh grant — there was no real way to make the constrained version usable once the panel is the persistent surface it's designed to be. Re-asked, user chose broad permissions this time. **The fail-soft code in `setAuto()` stays** as a defensive backstop (harmless if `host_permissions` makes it always succeed now) — don't remove it, and don't reintroduce activeTab-only for this path without a concrete plan for the no-op-reclick problem above.

**Firefox has no side panel access right now — a real gap, not yet solved.** `manifest.json` briefly declared `sidebar_action` (Firefox's own sidebar mechanism) alongside `side_panel`, but **Chrome hard-errors on unrecognized top-level manifest keys** (unlike `browser_specific_settings`, which exists specifically to be safely cross-browser-ignored) — this broke loading on Chrome/Brave and was reverted. There's no single manifest key both engines accept for this feature. Fixing it for real needs either two manifests (one per browser, meaning a build/packaging step this project has deliberately avoided so far) or confirming whether Firefox has since added support for the standardized `side_panel` key itself (unconfirmed — don't assume either way without checking current MDN/Firefox release notes first, the same mistake that caused this revert). Until resolved, Firefox's toolbar icon falls back to `openOptionsPage()` (the `else` branch already in `background.js`) — Firefox users have no history feed, only Options.

**Per-tab history**, backing the side panel's scrollback: every one of the three explain paths (`runForText`, `runForImage`, and the `DELPHI_EXPLAIN_TEXT` handler) calls `pushHistory(tabId, {question, ...result})`, appending to `chrome.storage.session`'s `history:${tabId}` (capped at `HISTORY_LIMIT = 50`, oldest dropped). The side panel doesn't need to be open to receive these — it reads the stored array on load and live-updates via `api.storage.onChanged`, so nothing is lost if the panel was closed when an answer completed. Scoped and cleared exactly like `auto:${tabId}` (navigation and tab-close both clear it) — same reasoning: a new page is a new set of questions, don't carry stale answers forward silently.

**Three ways in, two result-rendering paths.** `background.js` has one core (`runGenerate(mode, run)` → `explainText`/`explainImage`) that every path shares — builds the prompt, calls the active provider, parses the reply, and **never throws**: a provider/quota failure becomes a normal `{error}` result object instead of a rejected promise, specifically so a batch loop can keep going past one bad question rather than aborting the rest. What differs is how each path gets that result rendered:
1. **Selection**: context menu / `Ctrl+Shift+E` → `runForText(tabId, selectedText)` broadcasts `DELPHI_SHOW`/`DELPHI_RESULT` to `content.js`, which renders into the shared shadow-DOM panel bottom-right (`renderResult`). No natural on-page anchor for a selection, so the shared corner panel is the right call here.
2. **Region capture**: context menu / `Ctrl+Shift+D` → `content.js` shows a drag-select overlay → sends `{rect, dpr}` back → background does `captureVisibleTab` + crops with `OffscreenCanvas` (`cropDataUrl`) → `runForImage(tabId, croppedDataUrl)`, same broadcast path as selection. A captured region is a screenshot rectangle, not a DOM node — also no natural anchor.

**"Check this page"** (context menu / `Ctrl+Shift+C` / side panel button → `DELPHI_CHECK_PAGE` message) is `checkPage(tabId)`. Deliberately bypasses `explainImage`/`parseReply` entirely: the prompt (`buildPageCheckPrompt`) asks the model to find and answer *every* question across the screenshots as a numbered list, so there's no single trailing "Answer:" line to extract — `parseReply()`'s one-answer assumption doesn't apply here. The whole raw reply becomes `{explanation: reply, answer: null}` directly, which `buildResultBody()` already renders correctly unmodified (a paragraph, no reveal button, since `answer` is falsy) — no new rendering code needed. **This is the one path that works inside iframes**, since it's pure screenshot pixels, not DOM access — added specifically for LMS/knowledge-check pages (e.g. JSP-based courses) rendered in an iframe, where auto-detect's scan and the top-frame-only paths can't see anything. The side panel's button disables itself on click and re-enables via the same `storage.onChanged` on `history:${tabId}` the history feed already listens to — a fresh history entry is treated as "whatever was running finished," not a dedicated per-request completion signal (good enough; not worth a more precise tracker for this).

**`captureFullPage(tabId, windowId)` covers the whole scrollable page, not just the viewport** — `captureVisibleTab` has no "whole page" mode, so this scrolls to a series of Y positions (`getPageMetrics`'s `scrollHeight`/`viewportHeight`, stepped by one viewport height, capped at `MAX_PAGE_CHECK_SHOTS = 8` — added specifically because a single-viewport check was silently missing everything below the fold, a real user-reported gap), capturing at each. All three providers' `generate()` now take `images: string[] | null` instead of a single `imageDataUrl` (Ollama's `images` field was already an array — only `chrome-ai`/`custom` needed real changes, mapping one content-array entry per image); `explainImage()`/region-capture still wraps its single image as a one-element array to fit the same signature, no special-casing. **500ms between captures is deliberate, not arbitrary** — under Chrome's ~2-per-second `captureVisibleTab` quota *and* giving the page time to repaint/lazy-load before the shot. **More images costs real time on a local model** — this compounds directly with the `withKeepAlive` situation above; don't raise `MAX_PAGE_CHECK_SHOTS` without also reconsidering whether the keepalive ping is still sufficient at that length.

**`getPageMetrics`/`scrollTo` use `allFrames: true` — a real fix for a real second bug, not the original design.** The first version only looked at the top-level `window`/`document`, and a user confirmed live that full-page capture still missed content on the same JSP/LMS page that motivated "Check this page" in the first place — almost certainly because course-player content commonly renders inside an iframe with its own internal scroll, which the top frame's `scrollHeight` never reflects and `window.scrollTo()` on the top frame can't move. `getPageMetrics` now checks every frame and picks whichever one has the most content to scroll through (`scrollHeight - viewportHeight`, maximized) to decide how many shots are needed; `scrollTo` scrolls every frame to the same Y (a no-op for frames with nothing to scroll, since `scrollTo` just clamps). Scroll position is reset to `0` across all frames afterward rather than precisely restoring each frame's original position — simpler, and a per-frame restore would need one `executeScript` call per `frameId` since `args` can't vary per frame in one `allFrames` call. **This covers the iframe-with-its-own-scroll case; it does not cover a page whose scrolling happens inside a plain nested `<div>` with `overflow:auto` (not an iframe, not the window)** — that would need element-level scroll detection, which wasn't built since there's no confirmed case requiring it yet. If full-page capture is still reported as incomplete after this fix, that div case is the next thing to suspect.
3. **Auto-detect**: side panel toggle → `background.js`'s `setAuto(tabId, enabled)` → `content.js`'s `startAuto()` dynamically imports `detect-questions.js`, runs a debounced `MutationObserver`-driven scan, and adds a floating button *group* (`.auto-btn-group`: "Explain" + "Answer", in a separate always-fixed shadow overlay, tracked in the `blocks` Map keyed by element — `{btn, card, answerBadge}`) next to each detected block. **Unlike paths 1–2, this path does NOT broadcast to the shared panel** — clicking either button (`explainBlock(el, group, modeOverride)`, `modeOverride` is `null` for Explain or `"answer_only"` for Answer) sends `DELPHI_EXPLAIN_TEXT` with that mode via `api.runtime.sendMessage` and *awaits the direct response* (background's handler calls `sendResponse` instead of broadcasting). **Explain renders a full card** (`showCard`) below the block via `buildResultBody()`; **Answer renders a compact one-line badge** (`showAnswerBadge`) positioned where the buttons were, not a full card — an answer-only result has no explanation to show, so a card would just be a mostly-empty box. This is deliberate: a page with several detected questions dumping every answer into one shared corner panel would just overwrite itself — contextual placement is the only sane choice once there's more than one question in play. **The button click, not the detection, is what sends the message** — detection alone never calls a provider.

**"Explain all" and "answer all"** are the same `startBatch(modeOverride, activeBtn, otherBtn, idleLabel, verb)` function, called with different args — not two separate implementations. Both disable the other button while running (only one batch at a time) and both check `s.card?.querySelector(".err") || s.answerBadge?.classList.contains(".err")` for the failure count, since a batch item can end up in either shape depending on which mode it ran under.

**The bottom-right shared panel starts collapsed and stays that way** (`.panel` has no `display` unless `.open` is toggled) with a small always-visible `.mini-toggle` ("Δ"). It first only started collapsed but still auto-opened on every new result; a real user complaint ("the delphi thinking also presents the same information so it's repetitive when you have the side panel already showing") removed that auto-open too — `renderResult()` no longer touches `.open` at all, it just updates `.body` silently, and the only way to see it is clicking the toggle. This is intentional now: the side panel's history feed is the primary result surface, this panel is a secondary one for whoever doesn't have the side panel open, and it shouldn't compete with it for attention. `.close` still just removes `.open` (collapses to the toggle) rather than hiding the whole host, so it never requires re-triggering an explain action to get back to it.

**Side panel gained a "Capture region" button and a `busy:${tabId}` status banner, both requested directly by the user.** `DELPHI_CAPTURE_REGION` (side panel → background) is a thin one-line handler calling the same `startCapture(tabId)` the context menu / `Ctrl+Shift+D` already use — no new capture logic, just another trigger. **The busy banner is deliberately driven by the real `busy:${tabId}` storage flag, not a local "I just clicked a button" guess** — `setBusy(tabId, true/false)` wraps `runForText`/`runForImage`/`checkPage` (`try`/`finally`, so it clears even on error), read back via the same `storage.onChanged` live-update pattern `history`/`auto` already use. This is why clicking "Capture region" doesn't itself show the banner — `startCapture` only shows the drag-select overlay; `busy` doesn't flip true until the user actually finishes dragging and `runForImage` starts the real `generate()` call. The banner/button-disabling is correct regardless of which surface triggered the request (menu, keyboard shortcut, or these buttons), which a locally-tracked "did I click this" flag couldn't be. **Auto-detect deliberately does not set `busy`** — it already has its own per-button `…` state and the batch progress text in the badge, directly on the page; a global busy banner flipping on/off for every question in a 20-item "explain all" batch would be noise, not signal. `busy` is cleared in the same navigation/tab-close cleanup as `auto`/`history`, as a fail-safe against it getting stuck `true` if something dies before its `finally` runs.

**Side panel history entries are collapsed by default too, same complaint, same fix direction.** `renderHistory()` in `sidepanel.js` renders each entry as a native `<details>`/`<summary>` (`open` set only on index 0 of the reversed — i.e. newest-first — array) instead of a plain `<div>` — no custom JS toggle logic needed, the browser handles expand/collapse and the marker triangle for free. Don't reintroduce a custom collapse mechanism here; `<details>` already does exactly what was asked for.

**"Explain all"** (the badge's other button) is `content.js`'s `startBatch()` — snapshots currently-unanswered blocks (`state.btn` truthy), then awaits `explainBlock` **sequentially**, one at a time, updating the badge with `Explaining N of M (K failed)…` as it goes. Sequential, not `Promise.all`, on purpose: a local model (on-device Gemini Nano, or a CPU-only Ollama box like the one this was tested on) is a single shared compute resource, so parallel calls would just contend with each other, not go faster. `batchCancelled` is checked at the top of each loop iteration, flipped by either the badge's cancel click (re-clicking "explain all" while it's running) or `stopAuto()` — so turning auto-detect off mid-batch stops the batch too, it doesn't run of on its own after the UI disappears.

**Why region-capture and not a right-click-on-`<img>` fast path**: an earlier version added a `contexts: ["image"]` menu item that fetched `info.srcUrl` from the background service worker. Cut it — that fetch is subject to normal cross-origin CORS rules from a service worker (no `host_permissions` bypass without adding `<all_urls>`), so it would silently fail or return an unreadable opaque response for any cross-origin quiz image (the common case — CDN-hosted images). `captureVisibleTab` screenshots rendered pixels regardless of the image's origin, sidestepping CORS entirely, so region-capture already covers the `<img>` case (the capture-region menu item's `contexts` includes `"image"` for this reason). **Note:** now that `host_permissions: ["<all_urls>"]` is declared (added later, for the side panel — see above), the original CORS/permission blocker for a fetch-based `srcUrl` path no longer applies — re-adding it is now technically viable if a real need shows up, just wasn't done here since region-capture already covers the case and nobody asked for the extra click-saving.

**No OCR library.** Chrome's Prompt API (`LanguageModel`) takes image input directly (`expectedInputs: [{type: "image"}]`, then a content-array prompt with a `{type: "image", value: blob}` part) — confirmed current as of Chrome 148. Ollama's `/api/generate` takes raw base64 in an `images` array (needs a vision-capable model pulled, e.g. `llava`/`qwen2-vl`/`llama3.2-vision`). OpenAI-compatible custom endpoints take the standard `image_url` content-array shape. All three providers' `generate(prompt, config, imageDataUrl)` branch on whether an image was passed. This is why there's no Tesseract.js/OCR dependency anywhere — the vision-capable model *is* the OCR step. Don't add a separate OCR library; if a provider/model genuinely can't read the image, that surfaces as a normal provider error in the panel.

**Providers** (`src/providers/*.js`) share the shape `{id, label, isAvailable(config), generate(prompt, config, imageDataUrl)}`. `src/providers/index.js` reads the active provider + its config from `chrome.storage.sync` (written by `src/options/options.js`) and dispatches. Default provider is `chrome-ai` (Chrome's built-in Gemini Nano via the Prompt API) — free, on-device, zero setup, which is why it's the default rather than requiring a key or a local server on first install.

**Prompt design**: `buildPrompt()`/`buildImagePrompt()` in explain mode explicitly ask the model to cover *why the wrong choices are wrong*, not just why the right one is right — that's the specific gap in most mock-test tooling this project exists to fill. Don't simplify that instruction away.

**A real, confirmed-live bug: MV3 kills this service worker after ~30s idle, and a slow local model silently loses the whole request when it does.** Chrome's own DevTools "Inspect views" showed "service worker (inactive)" mid-"Check this page" request (5 questions, several minutes of local inference) — the worker was terminated while `await generate(...)` was still pending, which just abandons that execution; nothing catches it, no error, no result, the UI hangs on "Thinking…" forever. `withKeepAlive(run)` wraps every LLM call (`runGenerate`, and `checkPage`'s own `generate()` call, since it bypasses `runGenerate`) with a `setInterval` pinging a trivial extension API (`storage.session.get`) every 20s — a call to *any* extension API resets Chrome's idle timer per their own documented behavior, so this keeps the worker alive as long as the real call is running. **If this ever recurs despite the ping** (Chrome extension-updates/force-reloads/crashes the worker regardless, or there's a harder absolute execution cap beyond the idle timer that pinging can't help with — genuinely possible, wasn't verified live either), the next fix is bigger: move the actual provider call out of the service worker into a page context that isn't subject to MV3's idle-kill policy at all (the side panel's own script, since it stays alive as long as it's open) — don't reach for that unless the ping mitigation is confirmed insufficient.

**Caps/quotas — what's real and what isn't.** Each `generate()` call to `chrome-ai` creates and destroys its own `LanguageModel` session, so there's no cross-call quota to exhaust — running "explain all" on 50 questions doesn't get closer to any shared limit. The only real cap is a *single* question's prompt exceeding *that one session's* own context window, which throws `QuotaExceededError`; `chrome-ai.js` catches that specifically and rethrows a plain message instead of letting the raw `DOMException` surface. The `custom` (hosted API) provider is different — a rate limit there *is* a genuine shared, whole-account constraint, so `custom.js` gives HTTP 429 its own clear message too. Both funnel through `runGenerate()`'s catch-and-return-`{error}` shape, so a capped/rate-limited question shows a readable error on its own card/panel and a batch just continues to the next item — it was never going to throw and abort the loop.

**Auto-detect's scope boundary, enforced in code, not just docs**: `chrome.tabs.onUpdated` clears the per-tab `chrome.storage.session` flag on every `changeInfo.status === "loading"` (a real navigation/reload) — auto-detect never silently survives a page change, it has to be re-toggled. This was a deliberate choice over persisting it (which would need broader host permissions to reliably re-inject after navigation, and starts to look like the covert-monitoring pattern this project exists to avoid). SPA route changes (History API, no full reload) don't trigger this — the existing `MutationObserver` keeps working there, which is correct since the script/DOM context hasn't actually been torn down.

**`detect-questions.js`'s heuristic** (`looksLikeQuestion`) is intentionally simple and a bit noisy — a `?` plus 2+ lines matching `A) `/`B) `/`1) ` etc. (letters and numbers share one regex alternation), or (no lettered/numbered choices needed at all) both "true" and "false" present as whole words. It can occasionally flag unrelated text — a numbered list elsewhere on the page with a stray `?` nearby, a paragraph that happens to mention both "true" and "false." That's an acceptable trade, same reasoning as the original lettered-only version; don't chase perfect recall/precision here without a real report of it misbehaving on a real page — the button it adds is just an offer, a false positive costs the user nothing but an extra button they don't click.

**"Check this page" produces one history entry per question, not one blob** — `buildPageCheckPrompt()` asks the model for a strict `###`-delimited format (a label line, then explanation/answer, one block per question) rather than "number each question clearly" prose; a small local model's own numbering/formatting was inconsistent enough that regex-splitting on that alone wasn't reliable, but a single delimiter line is a much lower bar to actually follow. `parsePageCheckReply()` splits on `###` and reuses `parseReply()` per block (each block is just `label\n<the same shape parseReply already parses>`) — returns `null`, not an empty array, when there are fewer than 2 blocks, so `checkPage()` can tell "the model ignored the format" apart from "zero questions found" and fall back to showing the raw reply as one blob rather than silently losing content. **Don't remove that fallback** — model format-compliance isn't guaranteed, especially on smaller local models.

**Per-tab history now supports multiple entries per action and deletion.** `pushHistoryMany(tabId, entries)` is the real implementation (stamps each entry with `id: crypto.randomUUID()` and `ts`); `pushHistory(tabId, entry)` is a one-line wrapper around it for the single-entry call sites (`runForText`/`runForImage`/the `DELPHI_EXPLAIN_TEXT` handler). `checkPage()`'s structured path calls `pushHistoryMany` directly with one entry per parsed question. Deletion (`DELPHI_DELETE_HISTORY_ENTRY`) filters by that `id`, and clear-all (`DELPHI_CLEAR_HISTORY`) just removes the whole per-tab key — both are plain message handlers in `background.js`, no new storage shape beyond the `id` field. The side panel's per-entry "✕" lives inside the `<summary>` and calls `e.preventDefault()`/`e.stopPropagation()` on click — without that, clicking it also toggles the `<details>` open/closed, since a click on anything inside `<summary>` bubbles into the native disclosure-toggle behavior.

**Ollama's text/vision model split**: `ollama.js`'s `generate()` picks `config.visionModel` when `images` is non-empty, `config.model` otherwise (defaults `"llama3.2"`/`"llava"`). `chrome-ai` and `custom` don't get this — Chrome's on-device model is a single fixed thing with no model selection at all, and a hosted OpenAI-compatible model (`gpt-4o-mini` etc.) is typically already natively multimodal, so forcing a single choice isn't the same compromise there that it is for two separate local Ollama models.

**Output formatting: prompts ask for one point per line, `buildResultBody()` splits `explanation` on `\n+` into separate `<p>` elements.** Before this, `instructionFor()`/`buildPageCheckPrompt()`'s format asked for a "brief explanation" with no line-structure requirement, and the renderer put the whole thing in one `<p>` — legal, but a model was free to (and often did) write one dense paragraph covering every choice, which read as a wall of text. The two changes only work together: prompting for line-per-point without the renderer splitting on newlines just means the raw `\n`s show up as line breaks *within* one `<p>` (still readable, but no per-line spacing); splitting without the prompt change has nothing to split on if the model never produced newlines to begin with. **The Answer got its own labeled block too** — `answer-label`/`answer-value` (explain mode's revealed answer) and `answer-only-line`/`.answer-label` (answer-only mode's inline line) are new classes, styled separately in all three surfaces (`content.js`'s `.panel`/`.auto-card`, `sidepanel.html`'s `.entry`) since there's no shared stylesheet across the two shadow roots and the plain side panel page. **Same `all: initial` + explicit `color` requirement as the existing CSS-trap note applies to every one of these new rules in `content.js`** — got it right this time by writing them with the trap already in mind, don't regress if editing further.

**Lower sampling temperature across all three providers (0.3, down from each provider's default), specifically to reduce run-to-run variance in format compliance.** A user reported needing to click "Check this page" multiple times before getting a well-structured result — this is a structured-output task (strict `###`/line-per-point/`Answer:` format), not creative writing, so less sampling randomness should mean more consistent adherence to that format on a single attempt. `chrome-ai.js` reads the model's actual valid range via `LanguageModel.params()` (`{defaultTopK, maxTopK, defaultTemperature, maxTemperature}`) rather than guessing a `topK` that might be out of bounds — Chrome requires `topK` and `temperature` to be set together, you can't override just one — and fails soft (bare `try/catch`, falls through to default session creation) if `params()` isn't supported on that Chrome version. `ollama.js` uses `options: {temperature}`, `custom.js` uses a bare `temperature` field — both are standard, undocumented-risk parameters for their respective APIs, no equivalent caution needed there.

**`checkPage()` retries once, automatically, on a total format failure** — if `parsePageCheckReply()` returns `null` (the `###` format wasn't followed at all, not just a few missing individual answers within an otherwise-valid parse), it re-runs `generate()` once more with the *same* screenshots (no re-capture — the page hasn't changed, only the generation attempt needs to be fresh) before falling back to the raw-text blob. This is deliberately narrow: a partial success (some questions parsed, one or two missing an `answer`) is still useful and does **not** trigger a retry, since that would double an already-multi-minute wait for a marginal gain covered by the temperature fix above anyway. Don't broaden this to retry on partial failures too without reconsidering the latency cost.

**`parseReply()`'s `ANSWER_LINE` regex is deliberately anchored to line-start, not a bare substring search.** A user report on "Check this page" ("some [questions] don't reveal an answer") traced to the model not always writing the literal "Answer:" for every question in a longer multi-question reply — consistency across many questions in one response is harder for a model than one question at a time. Broadened the trigger phrases ("Answer", "The answer is", "Correct answer(?: is)?") but deliberately did **not** add a bare "Correct" alternative — explanation text routinely contains that word mid-sentence ("B is correct because...", "A is not correct"), and a bare substring match would grab the wrong text as the "answer." The `(?:^|\n)` anchor is what makes the broader phrase list safe to add at all; don't widen this further without keeping that anchor, and don't add "correct" alone as a trigger.

**Icon**: `icons/icon.svg` is the source of truth (a delta/triangle in the same blue→teal gradient used throughout the UI, on the dark `#1e1e2e` background), rendered to `icon16/48/128.png` via `rsvg-convert -w N -h N icons/icon.svg -o icons/iconN.png`. Regenerate from the SVG rather than hand-editing the PNGs if the mark ever changes. `options.html` and `sidepanel.html` both inline the same triangle-on-square shape directly as SVG next to their `<h1>` for the brand mark — copy-pasted, not a shared asset, since there's no bundler to import an SVG through and three near-identical inline SVGs is simpler than adding one.

**A real, already-hit CSS trap: `all: initial` resets `color` too, and it does *not* fall back to inherited color — it falls back to the UA default (effectively black).** `.panel p` and `.auto-card p` both use `all: initial` (to shed any styling the host page might otherwise leak in through inheritance) and originally didn't re-declare `color` afterward, so explanation text rendered near-black on the dark panel background — invisible until selected, since text selection's highlight color happens to make it readable. It went unnoticed for two versions because `.err` paragraphs looked fine (`.panel .err` has higher specificity than `.panel p`, so its explicit `color: #f38ba8` won regardless). **Any new `all: initial` rule that renders text must explicitly re-declare `color` in that same rule** — don't rely on inheritance working, because `all: initial` is exactly what breaks it.

## Known scope gaps (not bugs — deliberate boundaries)

- **No Firefox on-device AI.** Firefox has no Prompt API/Gemini Nano equivalent (and Brave doesn't ship Chrome's component either) — `chrome-ai.js`'s `isAvailable()` already degrades correctly there (checks `typeof LanguageModel === "undefined"`), no special-casing needed, but Ollama/Custom is the only real option on both.
- **No cross-tab/cross-window monitoring.** The original ask included "current tab and/or window" — scoped down to "the active tab, and only while you're looking at it" deliberately. Broader capture would need `desktopCapture`/screen-share-style permissions, which is a different trust level than this project should ask for.

## Testing

`tests/test_prompt_template.js` covers the pure logic: `prompt-template.js` and `detect-questions.js`'s `looksLikeQuestion`. Plain `node`, assert-based, no framework (run with `node tests/test_prompt_template.js`). DOM glue (`findQuestionBlocks`, `content.js`, `background.js`) stays untested by design — same as the providers already were — since exercising it needs a real browser, not jsdom-in-Node; don't add a jsdom dependency for this.

**All three input paths have been manually verified against a real Chrome instance and real Chrome built-in AI** (not just Ollama/mocks) — selection, region-capture (drag-select → `captureVisibleTab` → `OffscreenCanvas` crop → vision call), and auto-detect (heuristic scan → button → explain), all run against `manual-test/index.html` and confirmed working end to end, including the inline-choice regression case. One real caveat surfaced doing this: `LanguageModel`'s first real use triggers an on-device model download that isn't instant — don't read an initial `"unavailable"`/slow first response as broken without giving it a few minutes, and see the README for the two `chrome://flags` some Chrome builds still gate this behind. Ollama was also separately verified end-to-end (both text and image paths, using `qwen2.5vl:7b` — `moondream` was tried first and rejected for this: it ignored the `Answer:` format instruction and got a plain arithmetic question wrong, which is a model-quality problem, not a Delphi bug, but worth remembering if someone reports "no reveal button ever appears" with a small/weak Ollama model — check whether the model actually emitted an `Answer:` line before assuming `parseReply()` is broken).

## Brand kit / project presentation

`docs/images/{favicon,logo,banner,social-preview}.svg` (+ rendered `social-preview.png`) follow the exact convention `anvil`/`vulcan` established: `logo.svg` and `favicon.svg` are identical files (two names, one asset), `banner.svg` is 1200×300 left-aligned for the README header, `social-preview.svg`/`.png` is 1280×640 centered for GitHub's actual repo social-preview upload (PNG only — GitHub doesn't accept SVG there, regenerate via `rsvg-convert -w 1280 -h 640 docs/images/social-preview.svg -o docs/images/social-preview.png` if the SVG changes). Same house background (`#14161a`), rack-shelf texture lines, wordmark typography/sizing as the siblings — the delta mark itself uses the same blue→teal gradient as `icons/icon.svg`, and the right-side motif (three answer-choice bars, one picked + checked) is Delphi's answer to anvil/vulcan's tier-ticks, not a copy of them.

**`install.sh` is a dev-launcher, not a system installer** — unlike `vulcan`/`anvil`'s `./install` (which sets up a venv and can touch system Docker), this just launches an already-installed Chromium-based browser with `--load-extension` and a throwaway `--user-data-dir` (`.dev-profile/`, gitignored) so trying Delphi never touches the user's real browsing profile. Deliberately excludes Firefox (no `--load-extension` equivalent without the separate `web-ext` tool, and Firefox support here is still unverified anyway) and doesn't try to auto-detect/launch on macOS app bundle paths — Linux CLI binaries only, matching where this project has actually been built and tested.

**`.github/workflows/ci.yml` runs exactly the three checks that were being done by hand** throughout this project's development (manifest JSON validity, `node --check` on every script, the test suite) — added once there was enough surface area that "did I remember to check all three" stopped being a safe assumption. No lint step — this codebase has no linter configured, matching the plain-vanilla-JS/no-build-step philosophy elsewhere in this file.
